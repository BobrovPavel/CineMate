# CineMate — видение продукта

> Статус: черновик, живой документ. Технические детали ниже — **рекомендуемое направление
> и стартовые значения**, а не жёсткие правила: их можно и нужно пересматривать по
> результатам `evaluate.py` и первых пользователей.

## Суть

CineMate отвечает на один вопрос: **что посмотреть сегодня**. Без бесконечных каталогов и
фильтров: короткий онбординг, затем список из 10–20 фильмов, подобранных под конкретного
человека.

Каждая рекомендация **объясняется** — «понравилось 12 людям с похожим вкусом — они же
высоко оценили X и Y». Объяснимость — сильная сторона выбранного алгоритма (user-based
collaborative filtering), её показываем, а не прячем.

Качество рекомендаций **измеряется**, а не оценивается на глаз: офлайн-оценка на отложенной
выборке (precision@10, recall@10, coverage) в сравнении с baseline «просто популярное».

Цель проекта — **растить продукт**, а не только сделать демо. Отсюда главная продуктовая
метрика (см. ниже) и внимание к лицензиям данных (см. «Технические ограничения»).

**Главный принцип порядка работ: сначала алгоритм, потом сайт.** Импорт MovieLens →
скоринг → `evaluate.py` → подбор параметров. Пока precision@10 заметно не обгоняет
«просто популярное», фронтенд писать бессмысленно: красивый интерфейс поверх плохих
рекомендаций никто не будет использовать.

## Пользователи

**Основной пользователь** — человек, который вечером хочет посмотреть фильм и тратит
10–30 минут на пролистывание каталогов стриминга, так и не выбрав. Ему нужен короткий
список с понятной причиной «почему именно это», а не ещё один каталог.

- Язык интерфейса — **русский**, вёрстка **mobile-first** (выбор фильма часто происходит
  с телефона на диване).
- Регистрация не обязательна: анонимная сессия в cookie, профиль сохраняется сразу.
- Порог входа минимальный: онбординг можно **пропустить** в любой момент.

**Вторичный пользователь** — активный зритель с историей оценок на Кинопоиске. Может
импортировать свой профиль и сразу получить рекомендации без онбординга (P2, см. MVP).

**Главная продуктовая метрика** — доля «хороших» выдач: процент сессий, в которых хотя бы
одна рекомендация получила «нравится» (или иной позитивный сигнал). Вспомогательные —
доля новых пользователей, дошедших до первой выдачи, и возвращаемость за 7 дней.

## MVP

Приоритеты: **P0** — без этого нет продукта, **P1** — нужно для первого публичного
запуска, **P2** — после того как всё остальное работает на MovieLens.

### P0 — ядро: данные и алгоритм

| Фича | Детали |
|---|---|
| Импорт MovieLens | `ml-latest-small` (~600 пользователей, ~9k фильмов, ~100k оценок). Скрипт скачивает и парсит `movies.csv`, `ratings.csv`, `links.csv`; идемпотентный, повторный запуск без дублей. Импортированные пользователи помечены `is_synthetic` и участвуют в расчётах наравне с живыми. |
| Бинаризация оценок | MovieLens: `>= 3.5` → +1, `<= 2.5` → −1, середина отбрасывается как неинформативная. Стратегия бинаризации — за общим интерфейсом, чтобы другие источники могли использовать свою (см. P2). |
| Метаданные из TMDB | Постер, описание, год, жанры, длительность, рейтинг — по `tmdbId` из `links.csv`, кешируются в БД. Ключ — из переменной окружения. |
| Рекомендательный модуль | Отдельный от веб-слоя модуль с чистыми функциями: на входе разреженная матрица, на выходе список `(movie_id, score)` + данные для объяснения. Алгоритм — ниже. |
| Запасная стратегия | Если оценок меньше 5 или не нашлось достаточно похожих соседей — популярное с высоким средним рейтингом, перемешанное в пределах верха списка. API возвращает `strategy: "collaborative" \| "fallback"`, чтобы UI честно сказал «оцените ещё несколько фильмов». |
| `evaluate.py` | Разбиение 80/20 по каждому пользователю; precision@10, recall@10, coverage, средняя популярность рекомендованного; сравнение с baseline «популярное»; таблица результатов для подбора `K`, `LAMBDA`, `MIN_OVERLAP`. |
| Тесты алгоритма | Корректность похожести; дизлайки понижают балл; уже оценённое не попадает в выдачу; сжатие работает; fallback при пустом профиле; сценарий «X лайкнул 1..7, Z лайкнул 1,2,3,5,7,8,9 → X получает 8 и 9». |

**Рекомендуемый алгоритм (user-based CF), стартовые параметры:**

1. Матрица пользователи × фильмы, значения +1 / −1 / 0, `scipy.sparse.csr_matrix`.
2. Косинусная близость пользователей; если совместно оценённых фильмов меньше
   `MIN_OVERLAP` (старт: 5), похожесть = 0 — отсекает шум.
3. Top-K соседей с положительной похожестью (старт: `K = 40`).
4. Балл кандидата `m`: `norm(m) = Σ sim(X,U)·rating(U,m) / Σ |sim(X,U)|` по соседям,
   оценившим `m`. Учитываются и лайки, и дизлайки — нелюбимый соседями фильм уходит в минус.
5. Сжатие по объёму поддержки: `score = norm · n / (n + LAMBDA)` (старт: `LAMBDA = 5`),
   где `n` — число соседей, оценивших фильм.
6. Штраф за популярность (старт: деление на `log(1 + лайки(m))`), чтобы выдача не
   вырождалась в топ-250. Точная форма штрафа — предмет подбора в `evaluate.py`.
7. Исключить оценённое, «уже смотрел» и «не интересует».
8. Вернуть top-N по убыванию балла.

**Объяснение:** число похожих пользователей, лайкнувших фильм, и 2–3 фильма из уже
понравившихся пользователю, которые чаще всего лайкали те же соседи.

**План Б:** если user-based на `evaluate.py` окажется слабым — не мучить его, а попробовать
**item-based** (похожесть между фильмами). Матрица фильм × фильм стабильнее, хорошо
кешируется и лучше работает при ~10 оценках — а это ровно основной сценарий. Логика
скоринга при этом почти не меняется.

### P1 — продукт для первых пользователей

| Фича | Детали |
|---|---|
| Анонимная сессия | Токен в cookie, профиль создаётся сразу (`POST /api/session`). |
| Онбординг | Карточки по одной: постер, год, прогресс. Ответы: нравится / не нравится / не смотрел. Фильмы — известные и спорные: из топ-300 по числу оценок отбираются с наибольшей дисперсией и разбавляются по жанрам. «Хватит, покажи рекомендации» — после 5 оценок; **пропустить** — в любой момент (→ fallback). Свайпы на мобильных. |
| Лента рекомендаций | Сетка карточек с объяснением и кнопками «нравится / не нравится / уже смотрел / не интересует». Оценка в ленте обновляет подборку без перезагрузки. Скелетоны на время загрузки. |
| Профиль | Все оценки пользователя с возможностью изменить. |
| Главная | Короткое объяснение принципа и кнопка «начать». |
| Продуктовые события | Минимальный лог показов и реакций в выдаче — без него не посчитать главную метрику. |
| Атрибуция | MovieLens и TMDB в футере — требование условий использования обоих источников. |
| Инфраструктура | Docker + docker-compose, готовность к Railway/Fly.io; README (запуск, импорт, переменные окружения); `.env.example`, никаких ключей в коде. |

**Рекомендуемый API:** `POST /api/session`, `GET /api/onboarding`, `POST /api/ratings`,
`POST /api/seen`, `GET /api/recommendations?limit=20`, `GET /api/movies/{id}`,
`GET /api/profile`.

### P2 — после того как всё работает на MovieLens

| Фича | Детали |
|---|---|
| Сменный источник предпочтений | Протокол `RatingsSource.load() -> Iterable[RawRating]`, `RawRating = (external_user_id, external_movie_id, score, scale)`. Алгоритм и API не знают, какой источник активен; выбор — переменной окружения. `evaluate.py` считает метрики по каждому источнику и выводит сравнительную таблицу (плюс: число пользователей и оценок, плотность, медиана оценок на пользователя, доля российского и советского кино). |
| Привязка email | `POST /api/auth/claim` — чтобы не потерять оценки при смене устройства. |
| Импорт своего профиля Кинопоиска | `POST /api/import/kinopoisk` по ссылке или ID; фоновая задача с низким приоритетом, статус «импортировано N оценок» через опрос; после импорта онбординг пропускается. Ошибки: профиль закрыт, не найден, слишком мало оценок. |
| `KinopoiskSource` + краулер | Отдельный CLI в изоляции от веб-приложения, **последним этапом** — самая ненадёжная часть проекта, остальная разработка от неё не зависит. Двухфазная схема (обнаружение ID пользователей по `/film/{id}/votes/` → сбор профилей), `MIN_PROFILE_SIZE = 20`, цель 1000–2000 профилей. Обязательная псевдонимизация (`sha256(id + соль)` сразу при парсинге, никаких ников/аватаров/ссылок, включая логи), резюмируемость, вежливые задержки, остановка при капче, HTML не сохраняется. Бинаризация — относительно личного среднего пользователя (±0.5). См. «Открытые вопросы» — у этой фичи серьёзные риски. |
| Склейка фильмов | Единственный ключ — внутренний `movies.id`; внешние ID (`external_movielens_id`, `external_kinopoisk_id`) рядом; склейка между источниками — через `imdb_id`. |

### Рекомендуемый порядок работ

1. Структура проекта, схема БД, сигнатуры рекомендательного модуля — на согласование.
2. Модели и импорт MovieLens + TMDB.
3. Алгоритм и тесты к нему.
4. `evaluate.py` — **до** API и фронтенда, чтобы подобрать параметры и убедиться, что
   рекомендации лучше baseline.
5. API.
6. Фронтенд.
7. P2: сменный источник, импорт профиля, краулер — последним.

После каждой части — краткое резюме сделанного и оставшегося.

## Не делаем

В MVP сознательно **не** делаем:

- Каталог, поиск и фильтры по жанрам/годам — продукт отвечает на один вопрос, а не
  заменяет каталог.
- Свежие фильмы, которых нет в MovieLens, — рекомендуем только фильмы из датасета.
- Сериалы.
- Обязательную регистрацию, соцсети, комментарии, рецензии.
- Скрейпинг IMDb — метаданные только из TMDB API.
- Матричную факторизацию (SVD/ALS), гибрид с контентными признаками (жанры, режиссёры),
  режим «на двоих» — идеи на будущее.
- Item-based CF — только как план Б, если user-based не пройдёт `evaluate.py`.
- Фоновые задачи и предрасчёт рекомендаций — на 600 пользователях и 9k фильмах расчёт
  в реальном времени занимает миллисекунды; не усложняем преждевременно.
- Английскую локализацию.
- Большие датасеты (`ml-25m`) — только `ml-latest-small` на старте.

## Технические ограничения

**Рекомендуемый стек:**

- Backend: Python 3.12, FastAPI, NumPy/SciPy (разреженные матрицы), PostgreSQL,
  SQLAlchemy, Alembic.
- Frontend: Next.js (App Router, TypeScript), Tailwind.
- Деплой: Docker + docker-compose, целевые платформы Railway / Fly.io.

**Рекомендуемая модель данных:**

- `movies`: `id`, `tmdb_id`, `imdb_id`, `external_movielens_id`, `external_kinopoisk_id`,
  `title`, `original_title`, `year`, `overview`, `poster_path`, `genres`, `runtime`,
  `popularity_score`
- `users`: `id`, `session_token`, `email` (nullable), `created_at`, `is_synthetic`
- `ratings`: `user_id`, `movie_id`, `value` (+1 / −1), `created_at`; уникальность
  `(user_id, movie_id)`
- `seen_marks`: `user_id`, `movie_id`, `type` — **не оценка**: не участвует в расчёте
  похожести, влияет только на исключение из выдачи.

**Архитектурные принципы:**

- Рекомендательный модуль полностью отделён от FastAPI; полные type hints и docstrings.
- Матрица оценок кешируется в памяти и инвалидируется при новой оценке; расчёт вынесен
  так, чтобы позже уйти в фоновую задачу без переписывания API.
- Источник предпочтений и источник метаданных — сменные слои за интерфейсами.
- Краулер — изолированный компонент; веб-приложение от него не зависит.

**Внешние данные и API:**

- **MovieLens** (GroupLens) — `ml-latest-small`, требуется атрибуция.
- **TMDB API** — бесплатный ключ, требуется атрибуция и логотип.
- **Кинопоиск** — только P2, см. риски в открытых вопросах.

**Ограничения репозитория:**

- Python-пакеты должны соответствовать `cinemate*` (package discovery в `pyproject.toml`) —
  краулер стоит назвать, например, `cinemate_crawler` или вынести с отдельным
  `pyproject.toml`.
- CI сейчас проверяет только Python (ruff + pytest). Для Next.js понадобится отдельный
  job; изменения в `.github/workflows/` — только отдельной задачей.
- Новая логика покрывается тестами; ruff (line length 100, py312).

## Открытые вопросы

1. **Лицензии при цели «растить продукт».** Лицензия MovieLens запрещает коммерческое
   использование без разрешения GroupLens; бесплатный ключ TMDB тоже рассчитан на
   некоммерческое использование. Пока проект некоммерческий — всё в порядке, но до любой
   монетизации нужно решить: запрос разрешений или замена источника данных (например,
   собственные оценки живых пользователей).
2. **Краулер Кинопоиска.** Нарушает пользовательское соглашение Кинопоиска, а оценки
   пользователей — потенциально персональные данные: sha256 с солью — это
   псевдонимизация, не анонимизация. Для личного некоммерческого эксперимента риск
   приемлем при соблюдении robots.txt и мер выше, но **использовать собранные данные в
   публичном продукте нельзя**, не решив этот вопрос. Возможно, гипотезу «больше
   российского и советского кино» стоит сначала проверить через добровольный импорт
   собственных профилей (P2), а не массовый обход.
3. **Типы `seen_marks`.** В черновике смешаны «не смотрел» (онбординг), «уже смотрел»
   (лента) и «не интересует». Если «не смотрел» исключает фильм из выдачи, мы перестанем
   рекомендовать именно то, что человек не видел. Предложение: `type ∈ {not_seen,
   watched, not_interested}`, исключаются только `watched` и `not_interested`; `not_seen`
   хранится как сигнал (например, чтобы не показывать фильм повторно в онбординге).
4. **Штраф за популярность.** `score / log(1 + лайки)` при 0 лайков делит на ноль, а
   при 1 лайке *усиливает* балл (`log 2 ≈ 0.69`). Нужна защита (например,
   `log(2 + лайки)` или порог) и подбор формы штрафа в `evaluate.py`.
5. **Аккаунты.** Привязка email без подтверждения позволяет занять чужой адрес; для входа
   с другого устройства нужен magic-link или OAuth. Когда это делать и каким способом?
6. **Продуктовая аналитика.** Какие события логировать для главной метрики и где их
   хранить (своя таблица или внешний сервис)? Как определить «сессию»?
7. **Целевые пороги качества.** Насколько precision@10 должен обгонять baseline, чтобы
   переходить к фронтенду? Предложение — зафиксировать после первого прогона
   `evaluate.py`.
8. **Новинки.** Как и когда добавлять свежие фильмы, которых нет в MovieLens (контентный
   гибрид, данные живых пользователей)?
9. **Хостинг и бюджет.** Railway или Fly.io, бюджет на PostgreSQL и домен.
